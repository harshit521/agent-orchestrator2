# M2 — Scheduler and Run Lifecycle

## 1. Objective

M2 turns run execution into a restart-safe queue instead of fire-and-forget background work:

- queued runs are persisted and selected deterministically;
- `MAX_CONCURRENT_RUNS` is enforced;
- queued and running runs can be cancelled;
- orphaned runs are recovered on startup;
- queue state and lifecycle changes are visible through the API, SSE, and dashboard.

## 2. Data model

`RunStatus` is a Prisma enum:

```prisma
enum RunStatus {
  queued
  running
  completed
  failed
  cancelled
}
```

`Run` gained:

| Field | Purpose |
|---|---|
| `status` | One of the five lifecycle states |
| `startedAt` | Reset when the run is claimed, so it is the execution start and the FIFO key |
| `completedAt` | Set when a run completes |
| `cancelledAt` | Set when a run is cancelled |
| `cancelReason` | Persisted user-facing cancellation reason |

`@@index([status])` supports queue and active-run queries.
`@@index([taskId])` and `@@index([branch])` support detail and webhook lookups.

A task is `queued` or `running` while it has an unfinished run. On completion, failure, or
cancellation, the task status is updated to `completed` or `failed`.

## 3. Scheduler

`apps/api/src/scheduler/SchedulerService.ts` is the in-process scheduler. The database is the
source of truth.

### Ordering

`RunStore.listQueuedRuns()` selects queued runs and sorts them by:

1. task priority: `urgent` → `high` → `medium` → `low`;
2. FIFO by `startedAt`.

Unknown priorities sort last.

### Atomic claim

`RunStore.claimRun(runId)` performs:

```ts
updateMany({
  where: { id: runId, status: "queued" },
  data: { status: "running", startedAt: new Date() },
})
```

Only a count of `1` means the caller owns the run. A double drain or a second process therefore
cannot execute the same run twice. `claimNextQueuedRun()` walks the ordered candidates and claims
the first one that succeeds.

### Slot accounting

The scheduler keeps an in-process `Set<string>` of active run IDs. `#fillSlots()` claims while
`active.size < MAX_CONCURRENT_RUNS`. A completion removes the run from the set and requests
another drain. The database is still authoritative across restarts; the in-process set only
prevents over-admission within one process.

### Drain and error handling

- `drain()` is idempotent and coalesces concurrent requests.
- `enqueue(runId)` is a hint; it does not create a second queue.
- Execution rejection is logged and, if the run is still `running`, persisted as
  `SCHEDULER_ERROR`.
- A queue-claim error is logged and the next drain retries. It does not crash the process.

### Startup

`onReady` calls `RunService.recoverInterruptedRuns()` and then `scheduler.drain()`:

- `running` runs are marked `failed` with `INTERRUPTED_BY_RESTART` and a `run.failed` event;
- their tasks are marked `failed`;
- `queued` runs remain queued and are claimed normally.

## 4. Execution and cancellation

### Queued runs

`POST /tasks` and `POST /tasks/:taskId/run` create a queued run, record `run.queued`, and ask the
scheduler to drain. `POST /tasks` with `start: false` creates the task with no run.

### Running runs

`RunService.executeRun()` claims the run, records `run.started`, and executes the agent and
post-processing (workspace, tests, security gate, commit/push/PR). `startedAt` was set at claim
time.

### Cancellation

`POST /runs/:runId/cancel`:

- returns `404` for an unknown run and `409` for a terminal run;
- **queued**: marks the run `cancelled`, records `run.cancelled`, sets the task `failed`, and the
  conditional claim prevents later execution;
- **running**: aborts the `AbortController`, which cancels the LLM loop and kills child
  processes; persists `cancelReason`, `cancelledAt`, and `run.cancelled`; stops before
  commit/push.

`run.status` and `task.status` are updated in the same request. The SSE stream closes on
`run.cancelled`.

## 5. API and events

| Endpoint | Behaviour |
|---|---|
| `GET /runs` | Lists runs; queued runs include a 1-based `queuePosition` |
| `GET /runs/:runId` | Queued runs include `queuePosition`; all runs include events, artifacts, security |
| `POST /runs/:runId/cancel` | `202` on success, `404` unknown, `409` terminal |
| `GET /stats` | Includes `scheduler: { activeRuns, queuedRuns, maxConcurrentRuns }` |
| `GET /runs/:runId/events` | Replays then streams; closes on completed/failed/cancelled |

New events: `run.queued`, `run.cancelled`.

## 6. Dashboard

- Runs page: status filters for all five states, queue position badge, scheduler/concurrency
  strip, cancel action for queued/running runs.
- Run detail: queued banner with position, running SSE timeline, cancelled panel with reason and
  timestamp, completion/failure panels.
- Tasks page/detail: queued runs count as active, with a "Queued" action label.
- The frontend stream hook subscribes to the full event set and treats `run.cancelled` as
  terminal.

| Variable | Default |
|---|---|
| `MAX_CONCURRENT_RUNS` | `3` |

## 8. Tests

`apps/api/test/scheduler.test.ts` and `apps/api/test/recovery.test.ts` cover:

- at most `MAX_CONCURRENT_RUNS` runs execute, and a queued run starts when a slot frees;
- queued cancellation never invokes the agent and a repeated cancel returns `409`;
- startup recovery fails orphaned `running` runs and drains persisted `queued` runs;
- running cancellation aborts the agent and persists `cancelled` (`run-lifecycle.test.ts`);
- scheduler execution rejection persists `SCHEDULER_ERROR` and frees the slot
  (`scheduler-errors.test.ts`);
- queue-claim errors are logged and the next drain recovers (`scheduler-errors.test.ts`).

## 9. Limitations

- Slot accounting is per process. Multiple API processes would each enforce
  `MAX_CONCURRENT_RUNS`, although the atomic claim still prevents duplicate execution.
- Priority is a coarse four-level string; there is no aging or per-agent fairness.
- Shutdown does not wait for active runs to finish; their next startup is recovered as
  `INTERRUPTED_BY_RESTART`.
