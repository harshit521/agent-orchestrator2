# M3 — Security Gate, Events, and Lifecycle UI

## 1. Objective

M3 connects the existing security scanner to run execution and the dashboard:

- scan a coding run's worktree before its changes are committed;
- enforce a configurable policy (`fail-closed` or `warn-only`);
- persist scanner results per run and expose them through the API;
- emit security and lifecycle events that the dashboard consumes over SSE;
- surface queueing, concurrency, cancellation, and all five run states in the UI.

## 2. Where the gate runs

`RunService.#postProcessCodingRun()` executes:

1. stage and inspect the diff;
2. run repository tests (if enabled);
3. **run the security gate against the worktree;**
4. re-stage test-generated files and recompute the diff;
5. commit;
6. push and open a PR when GitHub is configured.

Running the gate before the commit means a blocking result prevents unverified code from being
committed. Cancellation is checked before post-processing; a cancelled run skips it.

The gate is constructed only when `SECURITY_ENABLED=true`:

```ts
createSecurityGate({
  policy,
  scanners,      // optional SECURITY_SCANNERS selection
  timeoutMs,
})
```

`apps/api/src/security/gate.ts` wraps `SecurityScanner`. If `SECURITY_SCANNERS` selects no known
scanner, startup fails with a configuration error rather than silently scanning nothing.

## 3. Policy semantics

Scanner results have four statuses:

| Status | Meaning | `fail-closed` | `warn-only` |
|---|---|---|---|
| `passed` | Tool ran and found nothing | continue | continue |
| `failed` | Tool ran and reported findings | **block** | continue |
| `error` | Tool crashed or the gate itself failed | **block** | continue |
| `unavailable` | Binary not installed | continue | continue |

`unavailable` never blocks, so a machine with no scanners installed does not reject every run.

When a scan is blocked, the run:

- ends with `status: "failed"` and `errorCode: "SECURITY_FAILED"`;
- records a `security.failed` event;
- does not commit or push;
- persists one `RunSecurity` row per scanner plus a `security_scan` artifact.

Under `warn-only`, findings are still persisted and a `security.failed` event is emitted, but the
run continues through commit/push/PR. The summary records `blocking: false`.

If the gate throws before returning results, it is treated as `error`. No scanner rows exist, so a
single `security-gate` row is persisted with the error. `fail-closed` blocks; `warn-only`
continues.

## 4. Persistence

### `RunSecurity`

```prisma
model RunSecurity {
  id           String   @id @default(cuid())
  runId        String
  scannerId    String
  status       String   // passed/failed/unavailable/error
  severity     String   // high/critical/medium/low/none
  description  String
  affectedFile String?
  lineNumber   Int?
  scannedAt    DateTime @default(now())
  error        String?
  run          Run      @relation(fields: [runId], references: [id], onDelete: Cascade)

  @@index([runId, scannedAt])
}
```

`runId` is intentionally not unique: a run can have one row per scanner. The relation is
`Run.runSecurity`, exposed by the API as `security[]`.

### `RunArtifact`

A `security_scan` artifact stores the complete summary:

```json
{
  "status": "passed | failed | error",
  "policy": "fail-closed | warn-only",
  "blocking": true,
  "results": [{ "id": "gitleaks", "status": "passed", "exitCode": 0 }],
  "error": "optional gate error"
}
```

## 5. Events

New event types:

- `security.started`
- `security.completed` — scan passed
- `security.failed` — findings or gate error

Events carry a compact result list (id, label, status, exit code, duration) so the timeline can
render without fetching another endpoint. Full outputs are in `RunSecurity.error`.

SSE replays persisted events before forwarding live ones and closes on
`run.completed`, `run.failed`, or `run.cancelled`.

## 6. API

`GET /runs/:runId` now returns:

```ts
{
  run: {
    ...,
    security: [
      {
        id, runId, scannerId, status, severity, description,
        affectedFile, lineNumber, scannedAt, error
      }
    ],
    artifacts: [ { kind: "security_scan", data: { ... } } ]
  }
}
```

The existing manual endpoints remain available when `SECURITY_ENABLED=true`:

- `GET /security/tools`
- `POST /security/scan`

When disabled, `POST /security/scan` returns `503`.

## 7. Dashboard

### Runs page

- Status filter for all five states: queued, running, completed, failed, cancelled.
- Queue position badge (`#n`) for queued runs.
- Scheduler strip: active slots, maximum concurrency, queued count, completed/failed/cancelled
  totals, all read from `GET /stats`.
- Cancel action for queued and running runs.

### Run detail

- Queued: explanatory banner with queue position and automatic updates.
- Running: live SSE timeline.
- Cancelled: cancellation panel with reason and timestamp.
- Failed: error code/message panel.
- Completed: output/artifacts.
- Security panel: per-scanner status, timestamp, description, expandable output, policy badge,
  and a blocking notice. Renders only when the backend persisted security data.

### Stream hook

`useRunStream` subscribes to every event type, deduplicates by event ID, and treats
`run.completed`, `run.failed`, and `run.cancelled` as terminal. The run detail page starts the
stream for queued and running runs.

## 8. Configuration

| Variable | Default | Purpose |
|---|---|---|
| `SECURITY_ENABLED` | `false` | Enable the gate and manual scan routes |
| `SECURITY_POLICY` | `fail-closed` | `fail-closed` or `warn-only` |
| `SECURITY_SCANNERS` | all | `gitleaks,semgrep,trivy` |
| `SECURITY_SCAN_TIMEOUT_MS` | `120000` | Per-scanner timeout |

## 9. Tests

`apps/api/test/security-gate.test.ts` covers:

- `fail-closed` blocks the run, returns `SECURITY_FAILED`, persists the finding, records
  `security.started`/`security.failed`, and never emits `git.commit`;
- `warn-only` persists the finding and continues through commit;
- a gate that throws fails closed and persists a `security-gate` error row.

`apps/api/test/security.test.ts` covers scanner execution (`passed`, `failed`, `unavailable`),
tool availability, and path-root enforcement.

## 10. Limitations

- Scanners are external binaries; unavailable tools do not block.
- Results are stored per scanner run but findings are summarised as one row per scanner, not one
  row per individual finding.
- The gate inspects the run worktree before commit; it does not re-scan the pushed branch or a
  container image.
- The manual `/security/scan` endpoint scans the repository root, not a specific run worktree.
